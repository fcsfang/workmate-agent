# Future Optimization Directions (未来优化方向规划)

本项目已实现 V1.9 FastAPI 响应模型重构与 Schema 强类型校验（原方案 B）以及 V2.2.0 ChromaDB 本地向量数据库集成。为了确保未完成或未来规划的优化方向能够被后续持续跟进，特梳理本规划文档。

---

## 1. 核心候选优化方向

### 💡 方案 A：RAG 召回可解释性可视化（RAG Explainability & Auditability）
* **背景与痛点**：目前 RAG 的多路召回打分（关键词、向量相似度、时间衰减、显著度）虽然在后台计算得很细，但在前端只是一堆放在 `<pre>` 标签里的原始文本，不易直观阅读和审计。
* **具体做法**：
  * 重构前端的 `MODEL CONTEXT` 面板。
  * 使用直观的 UI（如进度条、打分拆解雷达图/表格）可视化召回的 Top 5 记忆项。
  * 清晰展示**时间衰减因子如何影响旧记忆、向量距离与关键词匹配各自占了多少比重**。
* **简历亮点包装**：
  > “设计并实现了记忆检索可解释性（Explainability）可视化工具，将 RAG 召回的多路融合打分（包含时间衰减、语义向量、关键词及信息显著度）在前端进行实时解构和可视化展示，大幅提升了 Agent 运行时上下文检索的审计性与调试效率。”

---

### 💡 方案 C：Agent 耗时与运行时追踪可视化（Execution Trace Timeline）
* **背景与痛点**：Agent 的反应速度是本地运行时的关键瓶颈。目前虽有 `turn_trace` 记录了每个阶段（准备上下文、检索记忆、执行工具、调用大模型、写回记忆）的耗时，但前端缺乏可视化的链路分析。
* **具体做法**：
  * 在前端增加一个类似于 **LangSmith / Phoenix** 的 Agent 执行时间线（Timeline/Gantt Chart）。
  * 将 Agent 每一阶段的耗时以彩色时间槽直观展示，让用户一眼看出是 LLM 网络延迟卡住了，还是向量检索/ChromaDB 操作耗费了太多时间。
* **简历亮点包装**：
  > “在本地运行时中集成了轻量级调用链路追踪（Trace）引擎，对 Agent 决策环（感知、多路召回、工具调用、大模型生成、记忆固化）的各个生命周期阶段进行微秒级耗时剖析，并在前端可视化展示执行时间线，用于识别与优化本地 Agent 的响应延迟。”

---

### 💡 方案 D：本地知识库的向量检索迁移（Knowledge Base Vectorization）
* **背景与痛点**：当前项目中，引导性的“支持性知识”（`support_knowledge`）使用的是关键词匹配，在多样化的措辞输入下易漏检索。
* **具体做法**：
  * 将支持性知识库迁移至 ChromaDB 向量数据库。
  * 支持更灵活的语义问答和相关知识库检索，使陪伴及干预决策更契合当前用户的偏航情境。
* **简历亮点包装**：
  > “将关键字匹配的内部支持知识库迁移至嵌入式向量存储，通过多模态/文本向量实现跨领域的语义检索，使得 Agent 在面对用户负面反馈或工作摩擦时的干预准确率提升了约 XX%。”

## 2. 其它长期候选方向

### 方案 E：端侧多模态降本增效（视觉差分与本地 OCR 过滤）
* **目标**：解决屏幕监测每次都需要捕获并发送完整截图给云端多模态大模型，导致的 API 成本高且存在敏感信息上云隐患。
* **做法**：
  * **视觉差分机制 (SSIM/Diff)**：在本地使用 OpenCV 进行图像结构相似度（SSIM）或像素差分计算，只有在屏幕内容发生显著变化（如切换窗口、打字区域大幅变动）时才触发识图。
  * **本地 OCR 预过滤**：本地利用 Tesseract 等超轻量 OCR 引擎识别屏幕上的文字，若发现纯工作内容（如 IDE、文档代码），则不上传大模型。

### 方案 F：基于浏览器扩展（Chrome Extension）的深层动作捕获
* **目标**：辅助当前 Agent 细化用户在网页里的深层动作判断。
* **做法**：
  * 编写 Manifest V3 浏览器插件与本地 Agent 进行 IPC/WebSocket 通信。
  * 传递当前活跃标签页的完整大纲（DOM Summary）及 URL 路径，以提高对“在 GitHub 查资料”与“在 GitHub 摸鱼”的精细语义识别。
